## 9. 第 1 个单元：ParticleThermalizer（粒子热化）

### 9.1 交付物

| 项 | 位置 | 说明 |
|---|---|---|
| 核心契约 | `Source/Core/Runtime/IParticleThermalizer.H` | `defined()` + `apply(ParticleContext const&)`；不含任何具体 WarpX 类型 |
| 核心工厂 | `Source/Core/Runtime/ServiceFactory.cpp` | `register_particle_thermalizer_factory` / `create_particle_thermalizer`；未链接插件时返回 `nullptr` |
| 插件实现 | `Source/Plugins/ParticleCore/ParticleThermalizer.H/.cpp` | 原 `Modules/Particles/ParticleThermalizer/` 的两个文件（`git mv`，历史保留） |
| 静态注册 + 锚点 | `Source/Plugins/ParticleCore/ParticleThermalizerRegistration.cpp` | `warpx_particlecore_anchor`，与碰撞/场求解器插件同一模式 |
| 独立层目标 | `warpx_particlecore_<dim>` | 在顶层 `CMakeLists.txt` 注册；`lib_<dim>` 聚合其对象 |
| 开关 | `WarpX_PLUGIN_PARTICLECORE`（默认 ON） | OFF 时不编译插件、不拉锚点 |
| 内核改动 | `WarpX.H` / `WarpX.cpp` / `WarpXEvolve.cpp` | 成员改为 `std::unique_ptr<warpx::runtime::IParticleThermalizer>`；每步调用改为 `apply(particleContext())`；内核不再包含插件头 |

### 9.2 为什么它是粒子系统里最先能拆的一块

```text
内核调用点：只有 1 处（Evolve 中每步一次），不参与场推进/沉积/诊断
配置：particle_thermalizer 参数块自包含，不依赖容器内部状态
粒子访问：物种枚举/按名取容器 → IParticleContainerAccess；层数/几何/SoA tile → IParticleContainer
```

原实现有两处内核/PicEm 私有依赖，已在不改变行为的前提下消除：

```text
WarpX::getRealBox(box, lev)
  → 同一种 AMReX 构造 RealBox{bx, Geom(lev).CellSize(), Geom(lev).ProbLo()}
    （IParticleContainer::Geom 是 AMReX 容器接口，不是内核单例）

find_overlap()（PicEm 私有 AddPlasmaUtilities.H）
  → 内联同一布尔谓词；原调用计算出的 overlap box/shifted 在热化代码里从未被使用，
    所以只需保留"tile 是否与区域相交"这一判定
```

行为保持的细节：概率公式、阈值语义（`|u| > threshold*c`）、RNG 调用顺序、
无 `species` 过滤时遍历 `species + lasers`（与旧的 `for (auto& pc : mpc)` 是同一集合，
经 `ISpeciesMetadata::GetSpeciesAndLasersNames()` 获得）。

### 9.3 关闭开关时的行为

```text
WarpX_PLUGIN_PARTICLECORE=OFF
  → 核心 + 内核 + 诊断 + IO 仍可配置和构建（2D 实测，见路线文档 §11）
  → 输入里没有 particle_thermalizer.* ：正常演化，热化静默跳过
  → 输入里写了 particle_thermalizer.normal ：启动即报错，提示用
    WarpX_PLUGIN_PARTICLECORE=ON 重建（不允许静默改变物理）
```

### 9.4 运行时 A/B（1D，插件真实执行）

同一份输入，仅差 `particle_thermalizer` 参数块（3 步，每步输出 `ParticleEnergy`）：

```text
1D（build_multi2，warpx.1d）：
  无热化： step0 2.677077e6 J  →  step3 2.677052e6 J   （相对变化 -9.5e-6）
  有热化： step0 2.677077e6 J  →  step1 1.924147e6 J  →  step3 1.380356e6 J

2D（build_takeover，warpx.2d，normal = x）：
  无热化： step3 5.354053 J      有热化： step3 2.755459 J

3D（build_multi2，warpx.3d，normal = z）：
  无热化： step3 1.070777e-5 J   有热化： step3 4.872897e-6 J
```

结论：

```text
1) 三个维度上有热化时能量都显著下降，说明插件被静态注册、工厂返回非空、
   apply() 真的在工作（若注册失败，输入要求热化会在启动时被 9.3 的断言拦下）
2) 无热化时能量守恒（1D 相对变化 1e-5 量级），说明这条路径没有副作用
3) 1D/2D/3D 的 norm_pos 分支都被实际执行过（1D 只有 z；2D 的 x；3D 的 z）
```

## 10. 其余单元暂不可拆的量化原因

粒子树（已扣除迁出的热化单元）当前实测：

```text
cpp 文件：31
总行数：18747
include WarpX.H：17 个文件
WarpX:: 引用：71 行
具体容器类型（WarpXParticleContainer / MultiParticleContainer /
PhysicalParticleContainer）出现：256 行
```

按子目录：

| 子目录 | cpp | 行数 | WarpX.H | WarpX:: 行 | 具体容器行 | 主要阻塞 |
|---|---:|---:|---:|---:|---:|---|
| 根（容器/IO/边界/物种） | 13 | 11321 | 8 | 31 | 224 | `WarpXParticleContainer`/`MultiParticleContainer` 是上帝类；内核把 `mypc` 作为成员直接调用，需要先有 push/deposit/gather/boundary/creation 五组契约 |
| ElementaryProcess（QED） | 6 | 3034 | 3 | 15 | 0 | 引擎包装已与内核无关，但调用点在容器推进循环内；缺 `IParticleProcess` 契约与独立 `WarpX_PLUGIN_QED` 开关 |
| ParticleCreation | 3 | 2006 | 1 | 0 | 16 | `AddParticles` 依赖 `PlasmaInjector`（仍在 PicEm Initialization）、初始场与 `WarpX` 单例初始化；缺 `IParticleCreation` 契约 |
| Pusher（Implicit） | 1 | 1356 | 1 | 19 | 5 | 隐式推进驱动内核场求解与粒子保存/恢复（与隐式求解器同一阻塞，见路线文档 §11） |
| Resampling | 4 | 588 | 2 | 1 | 5 | `ResamplingTrigger` 仍经 `WarpX::GetInstance()` 取遗留运行时数据；需要容器侧调用钩子契约 |
| Deposition | 1 | 149 | 1 | 2 | 0 | 只有 `VarianceAccumulationBuffer` 一个独立 cpp；电荷/电流沉积算法本身在 `WarpXParticleContainer` 与场求解器里，拆它要先做 `IParticleDeposition`（需要场寄存器 + dt） |
| Gather | 1 | 116 | 1 | 3 | 2 | `GetExternalFields` 依赖晶格元件查找与内核配置；缺 `IExternalFieldProvider` |
| Sorting | 2 | 177 | 0 | 0 | 4 | 对内核零依赖，但只在容器内部被调用；没有内核可见的操作边界，单独成插件没有意义 |

其中的"具体容器行"是直接出现具体类型名的行数（`WarpXParticleContainer`、
`MultiParticleContainer`、`PhysicalParticleContainer`），也就是把该单元移出 PicEm 前
必须换成核心契约的地方数。
